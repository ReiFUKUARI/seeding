## D-001 ターゲットフレームワークは .NET 10（LTS）

**決定日**: フェーズ4
**関連**: 要件定義書 12章

要件定義書 12章は .NET 8/9 を選定しているが、.NET 9 は2026年5月にサポート終了済み、
.NET 8 も2026年11月に終了する。新規開発でフェーズ5〜6の開発期間中に
サポートが切れる見込みのため、**.NET 10（LTS・2028年11月まで）**を採用する。

**【要件定義書の改訂が必要】** 12章の「.NET 8/9」を「.NET 10」に。

### 実装への影響
`Directory.Build.props` の `WindowsTargetFramework` と `global.json` で管理。
将来の移行もこの2ファイルの書き換えで済む。

## D-002 カテゴリ値の「値名の変更」は実装しない

**決定日**: フェーズ4
**関連**: 要件定義書 5.3（「値名の変更は別途検討」とされていた箇所）

カテゴリ値の**リネーム機能は提供しない**。設定画面で行えるのは
**追加と削除のみ**とする（要件定義書 10.3 の記載どおり）。

### 実装への影響
- 値名を変えたい場合は「削除して追加し直す」運用になる。
  削除時には紐付いていた宛先から値が外れる（要件定義書 5.3）ため、
  削除確認ダイアログの警告文はこの運用を踏まえた表現にすること。
- スキーマ変更は不要。`UNIQUE (AxisId, Name)` 制約はそのままでよい。

## D-003 カテゴリ値の追加・削除はモーダルにも即時反映する

**決定日**: フェーズ4
**関連**: 要件定義書 5.3

要件定義書 5.3 は「新しい配信」「パートナーリスト」画面の検索フィルタ
（チェックボックス一覧）への即時反映を定めていた。これに加えて、
**モーダル内のカテゴリ選択欄も即時反映の対象**とする。

対象モーダル:

| モーダル | 反映対象 |
|---|---|
| 宛先を追加 | 種別・技術領域のチェックボックス一覧 |
| CSVから取り込む | テンプレートに出力されるカテゴリ値（実装済みの想定どおり） |

### 実装への影響（重要）

各画面・モーダルがそれぞれ開くたびにDBを読む実装でも「開いた時点の最新」は
得られるが、**カテゴリ値の一覧はアプリ全体で単一のソースを共有する構成**にすること。

- 具体的には、カテゴリ軸・値を保持する共有ストア（`ObservableCollection`）を1つ持ち、
  全画面・全モーダルがそれをバインドする。
- 追加・削除時はストアを更新し、バインド経由で全ビューへ伝播させる。
- 各ビューが個別にDBクエリを投げる実装にすると、反映漏れの温床になる。

## D-004 週次バックアップは「起動時に前回から7日経過していたら実行」

**決定日**: フェーズ4
**関連**: 要件定義書 5.5 / 10.2 / 13章

アプリは常駐しないため、Windows タスクスケジューラや MSIX の StartupTask は
使わず、**アプリ起動時に前回バックアップからの経過日数を判定して実行**する。

### 実装への影響
- 判定に使う状態は `AppSetting` テーブルの **`LastBackupAt`** キー（スキーマに用意済み）。
  手動バックアップ（10.2）の実行時もこの値を更新すること。
  手動で実行した直後に自動実行が走る、という二重実行を防げる。
- **起動処理をブロックしないこと**。バックアップは背景で実行し、
  完了・失敗はステータス表示にとどめる（モーダルで起動を妨げない）。
  手動実行時のみ、要件定義書 10.2 のとおり進捗モーダルを表示する。
- 7日以上PCを使わなかった場合、起動のたびに1回だけ実行される
  （経過日数に応じた複数回実行はしない）。
- 保存先が書き込めない（フォルダが消えている等）場合は、
  `LastBackupAt` を更新せず次回起動時に再試行する。

## D-005 送信中はウィンドウの閉じるボタンを無効化する

**決定日**: フェーズ4
**関連**: 要件定義書 4章（「送信中の中断機能は不要。開始したら最後まで自動完了」）

送信処理中は、ユーザーがウィンドウを閉じられないようにする。

### 実装への影響（重要）

WPF では XAML だけでは閉じるボタンをグレーアウトできない。
**次の2つを両方実装すること。**

1. **見た目の無効化**: Win32 相互運用でシステムメニューの `SC_CLOSE` を無効化する
   （`GetSystemMenu` + `EnableMenuItem`）。これで閉じるボタンがグレーアウトし、
   「押せない」ことがユーザーに伝わる。
2. **動作の抑止**: `Window.Closing` イベントで `e.Cancel = true` を返す。
   1 だけでは Alt+F4 やタスクバーからの終了を防げないため、
   こちらが実質的な防御になる。

送信完了後は両方を必ず元に戻すこと。送信が例外で終了した場合も同様
（`finally` で解除する）。

## D-006 CSVエクスポートに停止中の宛先も含める

**決定日**: フェーズ4
**関連**: 要件定義書 5.2 / 5.5

バックアップ用途のCSVエクスポートには、**停止中の宛先も含める**。

### 派生論点（未決・要確認）

要件定義書 5.5 のCSV列は「会社名・担当者名・メールアドレス・種別・技術領域・メモ」で、
**停止フラグに対応する列がない**。このままだとエクスポートしたCSVから復元しても
停止状態が失われ、停止していた宛先が配信対象に戻ってしまう。

| 案 | 内容 |
|---|---|
| **A（推奨・暫定採用）** | **エクスポートにのみ「状態」列を追加**（`配信中` / `停止中`）。取込テンプレート（5.5）は現状の6列のまま。取込時は「状態」列があれば読み、なければ全件を配信中として扱う |
| B | 列を追加せず、復元時に停止状態が失われることを許容する |

**Aを暫定採用**とする。CSV機能の実装（フェーズ5）着手前に確定させること。

Aを採用する場合 **【要件定義書の改訂が必要】**：5.5 にエクスポート列の記載を追加。

## D-007 添付ファイル合計の上限は13MB（承認済み）

**決定日**: フェーズ4（Windows実機でのSMTP疎通検証結果を踏まえて）
**関連**: 要件定義書 3章 / 14章

WebARENA実サーバー（dc30.etius.jp:587）への疎通検証で、
**サーバーのメールサイズ上限（SIZE拡張の広告値）が実測20.0MB**であることが判明した。
要件定義書 3章が想定していた25MBとは異なる。

**【要件定義書の改訂が必要】** 3章「メールサイズ上限」の「サーバー側上限25MB」を
「20MB（実測値）」に修正すること。

### 添付ファイル合計の上限を13MBとする根拠

```
サーバー上限 20.0MB ÷ Base64増量率 1.4（要件定義書3章の見積り）
  = 添付ファイル合計の理論上限 約14.3MB
  → 本文・ヘッダ分の余裕を見て切り下げ = 13MB
```

モックの仮値（20MB。要件定義書14章に記載）は「添付ファイルの生サイズ上限」の
つもりで置かれていたが、実際のサーバー上限20MBは
**Base64エンコード後を含むメール全体の上限**である。
モックの仮値をそのまま実装すると、20MBの添付ファイルはBase64で
約1.4倍（≒28MB）に膨らみ、**サーバー上限を超えて送信エラーになる**。

### 実装への影響

- 添付ファイル合計サイズのバリデーション（要件定義書 7章「サイズ上限超過時は
  確認画面遷移時にエラー表示」）は、**13MBを閾値**として実装する。
- ユーザーに見せるエラーメッセージにもこの数値が登場する。フェーズ4で承認済み。

### 併せて確認された事項（実装に影響なし）

- `Auto`指定時にSTARTTLSが実際にネゴシエートされることを実機で確認
  （TLS 1.2 / AES256）。`StartTls`明示指定と結果が同じだったため、
  **暗号化方式は要件定義書3章どおり`Auto`を継続**する。
- サーバーは `CRAM-MD5` / `LOGIN` / `PLAIN` を広告し、MailKitが自動的に
  最も安全な `CRAM-MD5` を選択して認証に成功した。実装変更は不要。
- 業務中のOutlookで「暗号化なし」と表示されていた件（要件定義書3章の記載の
  発端）は、実機検証では常にTLSが確立されたため、再現しなかった。
  Outlookの表示上の問題か、過去と現在でサーバー設定に差がある可能性がある。

詳細は [`smtp-verification.md`](./smtp-verification.md#4-検証結果の記録) を参照。

## D-009 MSIX署名方式・Publisher名（確定）

**決定日**: フェーズ4
**関連**: 要件定義書 12章、[msix-packaging.md 3. 署名と配布](./msix-packaging.md#3-署名と配布確定済み)

社内には署名方式に関する特定のルールはなく、「セキュリティが担保できていれば
よい」という方針のみ。加えて「なるべく手間がかからない仕様にすること」という
要望を受け、以下で確定する。

### Publisher名：`CN=ESC`

証明書のSubjectと `Package.appxmanifest` の `Identity` 要素は
`CN=ESC` に更新済み（`Name="ESC.MailDeliveryTool"` /
`Publisher="CN=ESC"` / `PublisherDisplayName="ESC"`）。

### 署名方式：自己署名証明書（社内管理）

公的コード署名証明書（有償・年次更新）は採用しない。理由：

- 配布先は社内の営業担当者のみ（要件定義書 2章「1人1台、営業担当者ごとに
  個別インストール」）。不特定多数への配布を想定していないため、公的CAが
  保証する「不特定の第三者に対する身元保証」の価値が働かない
- MSIXの署名は「改ざんされていないことの検証」と「インストールを許可する
  証明書を明示的に信頼させる」の2点を満たせればよく、自己署名証明書の
  公開鍵（`.cer`）を配布対象PCの証明書ストアへ導入する運用で両方とも満たせる
- 公的証明書の購入・年次更新コストが不要になる

これは要件定義書13章の「認証情報はDPAPIで暗号化保存」等と同じ考え方
（社内で完結する運用であれば、外部機関の関与は必須ではない）に沿っている。

### 手間を最小化するための工夫

「なるべく手間がかからない仕様に」という要望を踏まえ、以下で運用の手数を減らす。

| 項目 | 内容 |
|---|---|
| **証明書の有効期間** | **10年**（3〜5年ではなく長めに設定し、更新作業そのものの発生頻度を下げる。内部限定配布のため長期的なリスクより運用の手間削減を優先） |
| **各PCへの導入手順** | `Import-Certificate`（証明書の信頼登録）と`Add-AppxPackage`（インストール）を1本のスクリプトにまとめた：[`scripts/install-for-user.ps1`](../packaging/MailDeliveryTool.Package/scripts/install-for-user.ps1)。**CurrentUserストアを使うため管理者権限も不要** |
| **証明書の生成コマンド** | `msix-packaging.md`の「3. 署名と配布」にコピペ実行できる形で用意済み。担当者が1回実行するだけでよい |

証明書の生成・`.pfx`（秘密鍵）の保管者は、リリース作業を行う担当者が務める
想定（誰が実施するかは実装時に確定）。`.pfx`は**リポジトリには絶対に含めない**
（`.gitignore`済み）。

### 自動更新（`.appinstaller`）は保留

「手間の削減」という観点では自動更新の価値も高いが、配置先のファイル共有の
パスが未定のため、`.wapproj`への反映は保留した（プレースホルダーのパスを
入れてビルドを壊すリスクを避けるため）。ファイル共有の場所が決まり次第、
`msix-packaging.md`記載のプロパティ3行を追加するだけで有効化できる。
