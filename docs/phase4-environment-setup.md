### 実施できなかったことと理由

作業環境（Linux コンテナ）には **.NET SDK が入っておらず、
その取得元（`builds.dotnet.microsoft.com`）へのネットワークアクセスも
遮断されている**ため、以下は実行できていません。

- **ビルド・実行**：この環境（Linux）自体では `dotnet` コマンドを一度も
  実行できていません（SDKが未インストール）。実際のビルド・実行はすべて
  ユーザーの環境（Windows実機・GitHub Codespaces）で確認いただきました。
- **NuGet パッケージの復元**：`dotnet restore` は実行できていません。
  ただし nuget.org へは到達できたため、記載した各バージョンが実在すること、
  および `net10.0` と互換のターゲットを持つことは確認済みです
  （MailKit は net10.0 向けアセンブリを同梱する 4.17.0 を採用）。
  依存関係の完全な解決は実機での復元時に確認してください。
- **③ の疎通検証本体**：WebARENA の実アカウント情報がなく、
  かつサンドボックスから外部SMTPへ接続できません。

### 重要な発見：サーバーのメールサイズ上限は20MB（要件定義書の想定25MBと異なる）

疎通検証で判明した最大の成果です。**要件定義書 3章「サーバー側上限25MB」は誤り**で、
実測は **20.0MB** でした。

モックの添付ファイル仮値（20MB。要件定義書14章）は「添付ファイルの生サイズ」の
つもりでしたが、サーバーの20MBは**Base64エンコード後を含むメール全体の上限**です。
つまりモックの仮値をそのまま実装すると、20MBの添付ファイルはエンコードで
約28MBに膨れ、**必ずサーバー側のサイズ超過エラーになります**。

添付ファイル合計の実装上限は **13MB（承認済み）** です（20.0MB ÷ 1.4 ≒ 14.3MB から、
本文・ヘッダ分の余裕を見て切り下げ）。詳細と根拠は
[D-007](./decisions.md#d-007-添付ファイル合計の上限は13mb承認済み)。

**【要件定義書の改訂が必要】** 3章の「サーバー側上限25MB」を「20MB（実測値）」に。

なお、**ソースコードを書いて終わりにはせず、この環境で検証できるものは検証しました**。

- DBスキーマ：実際の SQLite エンジンに適用し、要件レベルの振る舞いを17項目検証（全パス）
- プロトコルログのマスク処理：4種の認証フローに対するテストで、
  当初の実装が CRLF 改行時にパスワードをマスクし損ねる不具合を発見し修正
- NuGet パッケージ：全6パッケージが nuget.org 上に実在し、`net10.0` と
  互換のターゲットを持つことを確認
- MailKit の API：コードで使用している型・メンバー23件が MailKit 4.17.0 の
  アセンブリに存在することを確認（名前レベルの確認であり、
  引数の型まで含めた検証はコンパイル時に行われます）
- 全 XML / XAML の妥当性、XAML のリソースキーとコードビハインドの対応関係

## ① プロジェクト雛形

```
MailDeliveryTool.sln
├── src/MailDeliveryTool.Core/        業務ロジック（UI非依存）
│   ├── Data/                          SQLite 接続・スキーマ・初期化
│   ├── Mail/                          MailKit による SMTP 処理
│   ├── Models/                        ドメインモデル
│   └── Security/                      DPAPI による暗号化
├── src/MailDeliveryTool.App/         WPF 本体
├── src/MailDeliveryTool.SmtpProbe/   SMTP疎通検証ツール（配布対象外）
└── packaging/MailDeliveryTool.Package/  MSIX パッケージング
```

UI から独立した `Core` を分けているのは、SMTP 疎通検証ツールから
同じ接続処理を呼べるようにするためです。検証で使ったコードが
そのまま本番の送信処理になるため、「検証は通ったのに本番で動かない」を避けられます。

### ターゲットフレームワーク：.NET 10（決定済み）

`Directory.Build.props` で **.NET 10（`net10.0-windows10.0.22621.0`）** を指定している。

要件定義書 12章は .NET 8/9 を挙げているが、いずれもサポート期限が
近い、または切れているため、協議のうえ .NET 10 を採用した。

| バージョン | 区分 | サポート終了 |
|---|---|---|
| .NET 8 | LTS | 2026年11月 |
| .NET 9 | STS | 2026年5月（終了済み） |
| **.NET 10** | **LTS** | **2028年11月** |

.NET 8 で着手するとフェーズ5〜6の開発期間中にサポートが切れる見込みであり、
新規開発である以上 LTS の .NET 10 で始めるのが妥当と判断した。

> 要件定義書 12章の記載（.NET 8/9）は、この決定に合わせて改訂が必要。

将来のバージョン移行も `Directory.Build.props` の
`WindowsTargetFramework` 1行と `global.json` の書き換えで済むよう構成している。

## ③ MailKit 疎通検証

### 成果物

`smtp-probe`（`src/MailDeliveryTool.SmtpProbe`）— 587 + `SecureSocketOptions.Auto`
で接続し、以下を報告するコンソールツール。

- **STARTTLS が実際にネゴシエートされたか**（要件定義書 14章の未検証事項）
- サーバーが広告した認証方式と、認証の成否
- サーバーが `SIZE` 拡張で広告するメールサイズ上限
- 認証情報をマスクした SMTP プロトコルログ全文

### 要件定義書 14章「パケットキャプチャ等で検証」について

**パケットキャプチャは不要です。** MailKit の `SmtpClient.IsSecure` を
読めば、STARTTLS が実際にネゴシエートされたかを直接判定できます。
`Auto` を指定したうえで `IsSecure == true` なら、STARTTLS が使われた証拠になります。
Wireshark を用意する必要はありません。

### セキュリティ上の配慮

- パスワードは**コマンドライン引数で受け取らず対話入力のみ**
  （コマンド履歴・プロセス一覧に残さないため）
- プロトコルログの `AUTH` 行と認証チャレンジ応答は自動マスク
  （AUTH PLAIN / AUTH LOGIN の2チャレンジ / CRAM-MD5 の各フローでテスト済み）

### 実機での疎通検証（完了）

上記サマリー表のとおり、Windows実機での実際の疎通検証は完了しています。
手順・結果は [`smtp-verification.md`](./smtp-verification.md) を参照。
併せて、実際のメールアカウントを使った送信も実機で確認済みです
（少数件の送信で問題なし。75通/分のペース送信自体の負荷テストは

## ④ MSIXパッケージング

`.wapproj`（Windows Application Packaging Project）方式を採用し、
構成ファイル一式を `packaging/MailDeliveryTool.Package/` に配置しました。
検討内容は [`msix-packaging.md`](./msix-packaging.md) を参照。

特に重要な発見として、**MSIX ではアンインストール時にアプリデータが
削除される**ため、SQLite DB に入っている宛先リストが消えます。
バックアップ先を（パッケージ管理外の）ドキュメントフォルダにしている
要件定義書 5.5 の設計はこの点でも妥当で、`AppPaths` にその意図を
実装済みです。運用手順書に「再インストール前にバックアップ」を
明記する必要があります。

署名方式・Publisher名・アプリアイコン・自動更新の要否はすべて確定済みです
（[D-008](./decisions.md#d-008-アプリアイコンはモックのロゴをそのまま採用)・
[D-009](./decisions.md#d-009-msix署名方式publisher名確定)・
[D-010](./decisions.md#d-010-自動更新appinstallerは不採用不具合発生時に都度手動再インストール)）。
詳細は同文書の「6. 決定事項一覧」を参照。

### 実機でのビルド確認（追記）

Windows実機で `.wapproj` のビルドに成功し、`artifacts/msix/` に
パッケージが生成されることを確認しました。過程で3つの環境依存エラーに
遭遇し、いずれもリポジトリ側の設定で対処済みです（対処法は
[`msix-packaging.md`](./msix-packaging.md#5-ビルド手順) に集約）。

- `MSB4040`（プロジェクトにターゲットがない）— `.wapproj` はVisual
  StudioのIDEから開くこと前提で、`$(WapProjPath)` がIDE外だと自動設定
  されないのが原因。素の `msbuild` から叩く場合は明示的に渡す必要がある
- `NETSDK1112`（ランタイムパックが見つからない）— `App`だけでなく
  `Core`にも `RuntimeIdentifiers(win-x64)` の宣言が必要だった
- `APPX3217`（UAPプラットフォームSDKが見つからない）— `.wapproj`の
  `TargetPlatformVersion` を実機に実際にインストールされている
  Windows SDKバージョン（`10.0.26100.0`）に合わせて解決

アプリアイコン・MSIXタイル画像は、社内確認の結果**モックプロトタイプの
ロゴ（紺色の「ESC」モノグラム）をそのまま採用**することになったため、
`src/MailDeliveryTool.App/Assets/app.ico` と
`packaging/.../Images/` に本採用の画像として差し替え済みです
（[D-008](./decisions.md#d-008-アプリアイコンはモックのロゴをそのまま採用)）。
