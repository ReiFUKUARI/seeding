# SMTP疎通検証 手順書（フェーズ4・成果物③）

要件定義書 3章の接続仕様と、14章の未検証事項を実アカウントで確認するための手順。

> **Windows実機で実施済みです。** 結果は「4. 検証結果の記録」を参照。
> `Auto`（本番設定）指定時の詳細フィールドのみ確認中です。

---

## 1. 何を確認するのか

| # | 確認項目 | 出典 | なぜ必要か |
|---|---|---|---|
| ① | 587 + `SecureSocketOptions.Auto` で接続できるか | 要件定義書 3章 | 本番と同じ設定で通ることの確認 |
| ② | **STARTTLS が実際にネゴシエートされるか** | 要件定義書 14章 | 業務中のOutlookが表示上「暗号化なし」のため実態が不明 |
| ③ | どの認証方式でネゴシエートされるか | 要件定義書 3章 | LOGIN / PLAIN / CRAM-MD5 のどれが使われるか |
| ④ | サーバーが広告するメールサイズ上限 | 要件定義書 14章 | 添付ファイルの実容量上限を確定するため |
| ⑤ | 実際にメールが届くか | ― | エンドツーエンドの確認 |

### ② について — パケットキャプチャは不要

要件定義書 14章では「パケットキャプチャ等で検証すること」としていましたが、
**MailKit の `SmtpClient.IsSecure` を読めば確実に判定できる**ため、
本ツールではその値を報告します。

`SecureSocketOptions.Auto` は「STARTTLS が使えるなら使い、使えなければ平文」
という動作です。したがって `Auto` を指定したうえで接続後に `IsSecure == true`
であれば、**STARTTLS が実際にネゴシエートされた**ことの直接的な証拠になります。
併せてTLSバージョン・暗号スイート・サーバーのSTARTTLS広告有無も出力します。

Wireshark を用意する必要はありません。

## 2. 実施手順

### 前提

- Windows 11 実機（社内ネットワークから実施すること。587番ポートの
  外向き通信が許可されている環境である必要があります）
- .NET SDK 10.0 以降
- WebARENA メールホスティングのアカウント情報
  （サーバー名 / アカウント名 / パスワード）

### 手順

```powershell
git clone <このリポジトリ>
cd seeding

# 1) ビルド
dotnet build src\MailDeliveryTool.SmtpProbe\MailDeliveryTool.SmtpProbe.csproj -c Release

# 2) 本番と同じ設定（Auto）で接続・認証まで確認する
dotnet run --project src\MailDeliveryTool.SmtpProbe -c Release -- `
  --host <WebARENAのSMTPサーバー名> `
  --user <アカウント名> `
  --from <送信元アドレス> `
  --log artifacts\probe-auto.log
```

パスワードは起動後に対話入力します（画面には表示されません）。
**コマンドライン引数では受け取りません**。コマンド履歴や
プロセス一覧にパスワードを残さないためです。

```powershell
# 3) テストメールを実際に送る（自分宛に送って受信を確認する）
dotnet run --project src\MailDeliveryTool.SmtpProbe -c Release -- `
  --host <サーバー名> --user <アカウント名> --from <送信元アドレス> `
  --send-to <自分のメールアドレス> `
  --log artifacts\probe-send.log

# 4) 参考: STARTTLS を必須にした場合の挙動も見ておく
#    ここで成功するなら、将来 Auto から StartTls へ強化できる余地がある
dotnet run --project src\MailDeliveryTool.SmtpProbe -c Release -- `
  --host <サーバー名> --user <アカウント名> --from <送信元アドレス> `
  --option StartTls `
  --log artifacts\probe-starttls.log
```

終了コード: `0` = 認証まで成功 / `1` = 検証失敗 / `2` = 引数エラー

### 出力例（想定）

```
================ 検証結果 ================
到達段階              : 接続・認証成功
要求した暗号化方式    : Auto

--- STARTTLS の実際の動作（要件定義書 14章） ---
サーバーのSTARTTLS広告: はい
実際に暗号化されたか  : はい
  TLSバージョン       : Tls12
  暗号スイート        : TLS_AES_256_GCM_SHA384
  => Auto指定でSTARTTLSが実際にネゴシエートされました。

--- 認証（要件定義書 3章） ---
サーバー広告の認証方式: CRAM-MD5, LOGIN, PLAIN
認証結果              : はい

--- メールサイズ上限（要件定義書 14章） ---
SIZE拡張の広告値      : 26,214,400 バイト（約 25.0 MB）
添付ファイル合計の目安: 約 17.9 MB 以下
```

### ログの取り扱い

`--log` で保存されるプロトコルログは、SMTPサーバーとの全やり取りを含みます。
`AUTH` 行と認証チャレンジへの応答行は**自動的に `****` へマスクされます**
（マスク処理は `SmtpConnectionTester.MaskCredentials`）。

ただし送信元アドレス等は残るため、`artifacts/` 配下（`.gitignore` 済み）に
置き、リポジトリにコミットしないでください。

## 3. 結果の読み取り方と分岐

### ② 「実際に暗号化されたか」が **いいえ** だった場合

認証情報が平文でネットワークを流れています。

1. `--option StartTls` を試す。これが成功するなら、サーバーは STARTTLS に
   対応しているのに `Auto` で選ばれなかったことになるため、原因を追う。
2. `--option StartTls` も失敗する場合、サーバーが STARTTLS 非対応。
   WebARENA のサポートに対応可否を確認する。
3. 対応していないことが確定した場合、要件定義書 3章の判断
   （`Auto` のまま運用する）は妥当だが、**平文送信であることを
   関係者に明示的に共有**したうえで進めること。

### ③ 認証方式について

`CRAM-MD5` が広告されていれば MailKit はそれを優先します（パスワードが
平文で流れないため）。`LOGIN` / `PLAIN` しか広告されない場合、
②が「いいえ」だとパスワードが平文で流れることになります。②と併せて判断してください。

### ④ サイズ上限について

`SIZE` 広告値をもとに、添付ファイル合計の実装上限を確定します。
ツールは `広告値 ÷ 1.4`（要件定義書 3章の Base64 増量率）を目安として出力します。
本文・ヘッダ分の余裕も見て、モックの仮値 20MB を見直してください。

`SIZE` が広告されない場合は、サーバー仕様書の 25MB を前提に決めます。

### 接続そのものが失敗する場合

| エラー | 主な原因 |
|---|---|
| タイムアウト | 社内FWが587番ポートの外向き通信を遮断している |
| `SmtpProtocolException` | ポート番号と暗号化方式の不一致（465なら `SslOnConnect`） |
| `AuthenticationException` | アカウント名・パスワードの誤り |
| `SslHandshakeException` | サーバー証明書の問題 |

## 5. 残る検証項目（フェーズ5で実施）

要件定義書 14章のうち、**送信ペースの検証（75通/分での安定性確認）**は
本ツールの対象外です。連続送信のペース制御は送信機能そのものの実装
（バッチ15件・バッチ内0.6秒・バッチ間3秒）を伴うため、フェーズ5で
実装と併せて検証します。
